# MCP Failure Lab 0.13.2 SDK compatibility report

Test date: 2026-11-04

## Executive summary

This study evaluated the npm distribution of `mcp-failure-lab@0.13.2` against current official
TypeScript, Python, and Go MCP SDKs. It covered stdio and Streamable HTTP, repeated every case
three times, and checked same-session recovery after every primary operation.

The study completed 180 executions. Of these, 168 met their reviewed call and recovery
expectations. The remaining 12 were consistent Go SDK recovery failures after responses with a
missing or invalid JSON-RPC version. The malformed responses were rejected correctly, but the
client session closed and could not complete the follow-up `ping`. TypeScript and Python rejected
the same malformed responses and remained usable in every repeat.

## Study scope

The matrix focused on malformed and duplicate responses, bounded oversized responses, invalid
progress notifications, and same-session recovery. It extends the compatibility evidence for the
new `oversized_response` and `invalid_progress` tools introduced after the earlier study.

This is a focused three-SDK study. It does not supersede the broader 432-execution
[0.12.0 compatibility study](v0.12.0.md), which covered six SDKs and additional fault families.

Ten cases ran over two transports with three independent repetitions. Every primary call was
followed by the `ping` tool on the same session.

| Client                                      | Version                                    | Runtime         | Protocol     | Executions |
| ------------------------------------------- | ------------------------------------------ | --------------- | ------------ | ---------: |
| TypeScript `@modelcontextprotocol/client`   | 2.4.0 (`@modelcontextprotocol/node` 2.1.2) | Node.js 22.23.4 | `2025-11-25` |         60 |
| Python `mcp`                                | 2.3.0                                      | Python 3.12.14  | `2025-11-25` |         60 |
| Go `github.com/modelcontextprotocol/go-sdk` | 1.8.0                                      | Go 1.27.1       | `2026-07-28` |         60 |

Rust, C#, Java, and Ruby were not executed in this run. The available environment had Rust
1.98.1 and .NET 10.0.401, but their harnesses were not completed. No Java runtime was installed.
Ruby 2.6.10 was present, but compatibility with the current Ruby SDK was not established.

## Test methodology

Each case used a fresh client session to prevent one fault from contaminating a later case. The
primary call and follow-up `ping` shared that session so recovery was measured explicitly. Calls
were bounded at 1.5 seconds. Result rows record the SDK, SDK version, transport, negotiated
protocol, arguments, repetition, duration, primary outcome, progress callbacks where available,
and recovery outcome.

| Case                      | Input                                        | Reviewed expectation                                                  |
| ------------------------- | -------------------------------------------- | --------------------------------------------------------------------- |
| Baseline                  | `ping`                                       | Primary call and follow-up `ping` succeed                             |
| Delay                     | `delayMs: 25`                                | Primary call and follow-up `ping` succeed                             |
| Missing JSON-RPC          | `malformed_message: missing-jsonrpc`         | Primary call is rejected; follow-up `ping` succeeds                   |
| Invalid JSON-RPC version  | `malformed_message: invalid-jsonrpc-version` | Primary call is rejected; follow-up `ping` succeeds                   |
| Result with error         | `malformed_message: result-with-error`       | Primary call is rejected; follow-up `ping` succeeds                   |
| Duplicate response        | `duplicate_response`                         | Primary call and follow-up `ping` succeed                             |
| Oversized response        | `sizeBytes: 65536`                           | Primary call and follow-up `ping` succeed at the default client limit |
| Unknown progress token    | `invalid_progress: unknown-token`            | Record callback behavior; primary call and follow-up `ping` succeed   |
| Regressing progress       | `invalid_progress: regressing-progress`      | Record callback behavior; primary call and follow-up `ping` succeed   |
| Progress after completion | `invalid_progress: after-completion`         | Record callback behavior; primary call and follow-up `ping` succeed   |

The progress cases are observations, not claims that every SDK must turn the invalid
notification into a call-level error. The 64 KiB response case establishes acceptance at that
size; it does not establish a client's rejection threshold.

## Results

All 54 malformed primary calls were rejected. Those errors are successful fault detection,
not SDK failures.

| Client           | Malformed primary rejection | Same-session recovery |
| ---------------- | --------------------------: | --------------------: |
| TypeScript 2.4.0 |                       18/18 |                 18/18 |
| Python 2.3.0     |                       18/18 |                 18/18 |
| Go 1.8.0         |                       18/18 |                  6/18 |

TypeScript and Python remained usable after every malformed response. TypeScript usually
surfaced malformed responses as request timeouts. Python surfaced HTTP parser errors and a mix
of stdio timeouts and validation errors. The response classification differed, but the explicit
recovery assertion passed in every repeat.

Go rejected responses missing `jsonrpc` or declaring `jsonrpc: "1.0"`, then closed the client
session. The follow-up `ping` failed in all 12 combinations: two variants, two transports, and
three repeats. Errors included `client is closing: invalid message version tag`. Go rejected
`result-with-error` and recovered successfully in all six runs.

This is a reproducible failed recovery assertion and a candidate Go SDK defect. It matches the
behavior recorded for Go SDK 1.7.0 in the [0.12.0 report](v0.12.0.md). The Observatory record
retains the failed runs but does not classify them as a reviewed Finding because no corresponding
upstream issue was verified during this study.

All 18 64 KiB response calls and their follow-up pings succeeded. All 54 invalid-progress calls
and their follow-up pings succeeded. TypeScript and Python ignored unknown-token notifications,
delivered regressing progress values `2, 1` to their callbacks, and did not deliver the late
notification to the completed request callback. The Go harness attached a progress token and
verified completion and recovery, but did not record callback values.

Baseline, delay, duplicate-response, and follow-up calls succeeded in all 72 corresponding rows.
The duplicate-response result establishes continued usability; diagnostics emitted outside the
call result were not normalized across SDKs.

## Finding classification

- Expected primary errors: the 54 malformed-message rejections.
- Failed harness assertions: the 12 Go same-session recovery checks after missing or invalid
  JSON-RPC version responses.
- Candidate SDK defect: Go 1.8.0 closes the session after those malformed responses on both
  transports.
- Behavioral observations only: invalid-progress callback handling and 64 KiB response
  acceptance.

## Limitations

This focused study did not exercise `hang`, timeout recovery, `disconnect`,
`response_after_cancellation`, `protocol_ping_liveness`, or `session_loss`. It therefore does not
support a seven-SDK aggregate pass rate or a claim that all 0.12.0 compatibility scenarios were
rerun. The 64 KiB case demonstrates successful handling at that size with default client limits;
it does not determine maximum accepted message size. The Go progress cases verify completion and
recovery but do not preserve callback values.

implementation-specific reports—TypeScript, Python, and Go—are also included in
