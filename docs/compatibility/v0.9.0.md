`mcp-failure-lab@0.9.0` npm package.

## Interpretation

No MCP Failure Lab 0.9.0 defect was found.

- The TypeScript SDK reported timeouts for delay and hang. It treated malformed replies as
  unanswered requests that reached the configured timeout; the next request succeeded.
- The Python SDK reported explicit validation errors for malformed `jsonrpc` values and recovered
  after each malformed response.
- A stdio disconnect ends the server process and therefore the transport. Reconnection requires a
  new process and client by design.
- After an HTTP disconnect, the TypeScript client failed the interrupted request and successfully
  completed the next `ping`. Python `mcp` 2.2.0 instead marked the client connection closed,
  rejected the next request, and raised an `ExceptionGroup` while its transport context exited.
  This difference is tracked upstream as
  [modelcontextprotocol/python-sdk#3522](https://github.com/modelcontextprotocol/python-sdk/issues/3522).
- Go SDK 1.7.0 completed normal stdio and HTTP calls, timeout cancellation, later recovery, and
  same-client HTTP recovery after an injected disconnect. It strictly rejected responses with a
  missing or `1.0` `jsonrpc` version and then closed the session, so a later call on that session
  failed. The injected result-with-error variant remained request-scoped and recovery succeeded.
- Go's protocol-level HTTP `Ping` was not counted as a compatibility failure. The SDK negotiated
  `2026-07-28`, whose schema no longer includes protocol ping. The same observation was already
  closed as unsupported in
  [modelcontextprotocol/go-sdk#1249](https://github.com/modelcontextprotocol/go-sdk/issues/1249).
- Rust `rmcp` 3.4.0 passed initialization, normal calls, timeout cancellation, malformed-version
  detection, and later recovery over both transports. HTTP also recovered on the same client after
  an injected disconnect. However, `rmcp` accepted the deliberately invalid JSON-RPC response
  containing both `result` and `error` as a successful result over both transports. This is an
  external Rust SDK response-validation gap; the same response was rejected by C# and Python.
- C# `ModelContextProtocol` 2.2.0 passed every supported scenario over both transports. It
  surfaced cancellation through `TaskCanceledException`, rejected all malformed variants, and
  recovered after each request-scoped failure. Its HTTP client also recovered after an injected
  disconnect.
- Inspector's one-shot CLI has no per-tool timeout setting, so bounded automation of `hang` and
  same-session recovery is outside that interface. Its normal operations worked over both
  transports and both protocol eras tested.

## Reproduce the Python HTTP result

Start the published server:

```sh
npx mcp-failure-lab@0.9.0 serve \
  --transport http --host 127.0.0.1 --port 43118 --path /mcp
```

In a Python 3.12 environment:

```sh
pip install mcp==2.2.0
```

Run:

```python
import anyio
from mcp import ClientSession
from mcp.client.streamable_http import streamable_http_client


async def main() -> None:
    try:
        async with streamable_http_client("http://127.0.0.1:43118/mcp") as streams:
            async with ClientSession(
                streams[0], streams[1], read_timeout_seconds=1.0
            ) as session:
                await session.initialize()
                try:
                    await session.call_tool("disconnect", {}, read_timeout_seconds=0.6)
                except BaseException as error:
                    print("disconnect:", type(error).__name__, error)

                print("ping:", await session.call_tool("ping", {}))
    except BaseException as error:
        print("cleanup:", type(error).__name__, error)


anyio.run(main)
```

Observed with Python SDK 2.2.0: the next call reports `MCPError: Connection closed`, followed by an
`ExceptionGroup` during cleanup. See the upstream issue for the complete diagnostic context.

## Reproduce the Go malformed-response result

Use Go 1.25.14 and pin the official SDK in a small client module:

```sh
go mod init failure-lab-go-repro
go get github.com/modelcontextprotocol/go-sdk@v1.7.0
```

Connect with `mcp.CommandTransport`, initialize a `ClientSession`, and call
`malformed_message` with either `{"variant":"missing-jsonrpc"}` or
`{"variant":"invalid-jsonrpc-version"}`. The call reports `invalid message version tag`; a
subsequent `ping` tool call on the same session reports that the client is closed. The same result
occurs with `mcp.StreamableClientTransport` against the HTTP endpoint. Start every focused HTTP
case with a new client session.

## Reproduce the Rust result-with-error acceptance

Use Rust 1.98.1 and pin the official SDK:

```sh
cargo add rmcp@=3.4.0 --features client,transport-child-process,transport-streamable-http-client-reqwest
```

After initializing a client, call:

```rust
client
    .call_tool(
        CallToolRequestParams::new("malformed_message")
            .with_arguments(serde_json::json!({"variant": "result-with-error"})
                .as_object().unwrap().clone()),
    )
    .await
```

Against Failure Lab 0.9.0, `rmcp` returns `Ok(CallToolResult)` even though the wire response
contains both `result` and `error`. A later `ping` tool call succeeds. The same result occurs
with `TokioChildProcess` and `StreamableHttpClientTransport`.

## Scope

These results describe the exact versions above. They do not imply that every earlier or later
client release behaves identically. The Rust run used rustc 1.98.1; the C# run used .NET SDK
10.0.401. Raw dependency directories and machine-specific logs are not stored in the repository;
the commands and version pins above preserve the actionable reproducer.
