## Test procedure

Each independent case used a fresh client. Recovery assertions used the existing client
unless explicitly checking reconnection. Recorded durations include case execution and cleanup.

| Case               | Primary operation                                                                     | Assertion                                                         |
| ------------------ | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Baseline           | Initialize and call `ping`                                                            | Successful response                                               |
| Delay              | `delayMs: 30` (Java: 250)                                                             | Completion, then same-client `ping`                               |
| Delay timeout      | `delayMs: 250`, 80 ms request bound (Java: 2,000 ms, 1 s bound)                       | Rejection, then same-client `ping`                                |
| Hang               | `hang`, 80 ms request bound (Java: 1 s)                                               | Rejection, then same-client `ping`                                |
| Duplicate response | `duplicate_response`; wait 50 ms (Java: 100)                                          | Primary result accepted; same-client `ping`                       |
| Malformed response | Each of `missing-jsonrpc`, `invalid-jsonrpc-version`, `result-with-error`             | Primary rejection; same-client `ping`                             |
| Late cancellation  | `response_after_cancellation`, 80 ms bound; wait 150 ms (Java: 1 s bound, 1.2 s wait) | Rejection; same-client `ping`                                     |
| Session loss       | `session_loss`, `activation: "after_response"`                                        | Next request rejected; fresh-client `ping`                        |
| Disconnect         | `disconnect`                                                                          | Request rejection or session-context failure; fresh-client `ping` |

TypeScript, Python, C#, and Java also listed tools during baseline checks.
Session-loss cases included unrelated-session checks for TypeScript, Python, and C#.
Java additionally required same-client HTTP recovery after disconnect.

Java checks extended the [existing experiment](../../experiments/java-sdk/README.md) in a
temporary harness. The checked-in experiment does not reproduce the full 0.12.0 matrix.

C# used a 500 ms stdio shutdown timeout. Other harnesses bounded cleanup or terminated their
owned server processes. Test servers and the Java container were stopped after execution.

## Protocol liveness

`protocol_ping_liveness` sends an MCP protocol request while the tool call is in flight.
The subsequent `ping` is the ordinary tool used to check connection usability.

| Client     | Cases on both transports                                   | Expected protocol-ping outcome      |
| ---------- | ---------------------------------------------------------- | ----------------------------------- |
| TypeScript | Default response, controlled rejection, controlled timeout | `success`, `unsupported`, `timeout` |
| Python     | Default response, controlled rejection, controlled timeout | `success`, `unsupported`, `timeout` |
| Go         | Modern protocol                                            | `unsupported`                       |
| Rust       | Legacy protocol, including requested-modern configuration  | `success`                           |
| C#         | Legacy and modern protocols                                | `success`, `unsupported`            |
| Java       | Legacy protocol                                            | `success`                           |

All liveness assertions passed, including same-client follow-up `ping`.

TypeScript and Python used `pingAfterMs: 10`, `livenessTimeoutMs: 80`,
and `completionDelayMs: 20`. Controlled handlers returned method-not-found or delayed
the response by 250 ms. Python used a subclass overriding the incoming-request hook;
rejection and timeout cases do not represent its stock handler behavior.

`closeOnFailure` was false except for controlled rejection over stdio.
Those cases used true, returned `closure_unavailable`, and retained a usable connection.
Failed-ping HTTP closure was not exercised.

Rust and C# used a 100 ms liveness timeout. Java used `pingAfterMs: 100`,
`livenessTimeoutMs: 1000`, and `completionDelayMs: 100`.

Rust's raw `liveness_modern` label records a configuration request.
Peer information reported `2025-11-25` on both transports; these executions provide
legacy coverage only.

## Failure analysis

### Python: uncached output-schema lookup after session loss

Three HTTP `after_response` executions failed during activation with a nested
`ExceptionGroup` containing `MCPError(-32001, 'Session not found', None)`.
A separate three-run diagnostic confirmed that activation did not return successfully.
Lost-session, unrelated-session, and reconnection assertions were not reached.
Some cleanup paths logged `Session termination failed: 404`.

Controlled repeats against published 0.11.0 and 0.12.0 used the same Python environment
and a local HTTP forwarding proxy. Each version reproduced this sequence three times:

1. `tools/call(session_loss)` returned HTTP 200 with a valid activation result.
2. Before returning from `call_tool()`, Python's `validate_tool_result()` found no cached
   schema and issued `tools/list` on the expired session.
3. `tools/list` returned HTTP 404 and JSON-RPC error `-32001`.
4. The public `call_tool()` operation raised that schema-lookup error.

Calling `list_tools()` before activation populated the schema cache. In three repeats per
server version, activation then returned successfully and the explicit follow-up `ping`
raised `MCPError(-32001, 'Session not found', None)`. Cleanup still logged HTTP 404.

The original assertion measured the complete SDK helper, not only the wire-level response.
This is an output-validation dependency on an expired session, not a 0.12.0 server regression
or evidence of a failed activation response. The earlier successful
[0.11.0 report](v0.11.0.md) is not a controlled comparison because schema-cache state
was not held constant. No new upstream defect is established by this fault-injection case.

### Go: malformed-response recovery

Missing `jsonrpc` and `jsonrpc: "1.0"` were rejected, but the connection then closed.
Follow-up `ping` failed on both transports in all repeats: 12 failed recovery assertions.
This matches the [0.9.0 observation](v0.9.0.md).
Result-with-error rejection and recovery passed.

### Rust: response validation and session recovery

A response containing both `result` and `error` was accepted on both transports:
six failed validation assertions, matching
[#1283](https://github.com/modelcontextprotocol/rust-sdk/issues/1283).
The assertion terminated the case before follow-up `ping`; recovery was not evaluated.

Following HTTP `after_response` session loss, the next request succeeded in all three repeats:
three failed rejection assertions.

Controlled repeats against 0.11.0 and 0.12.0 used the same Rust binary and dependency tree.
With the default `reinit_on_expired_session: true`, wire traces showed:

1. Activation returned successfully on session A.
2. `ping` on session A returned HTTP 404.
3. The transport initialized a new session B without sending session A's header.
4. It retried `ping` on session B successfully.

All three repeats per server version followed this sequence. With
`reinit_on_expired_session: false`, all three repeats per version returned
`TransportSend(... SessionExpired)` for the next call.

Server-side invalidation worked. The original rejection assertion was incompatible with
the SDK's default transparent recovery policy; it does not identify an upstream defect.
Original raw outcomes and summary counts are retained.

### Java: malformed-response validation and recovery

`jsonrpc: "1.0"` was accepted on both transports: six failed validation assertions,
matching [#1156](https://github.com/modelcontextprotocol/java-sdk/issues/1156).

Over stdio, missing `jsonrpc` and result-with-error caused both the primary call and
follow-up `ping` to time out: six failed recovery assertions, matching
[#1157](https://github.com/modelcontextprotocol/java-sdk/issues/1157).
Both variants were rejected with successful recovery over HTTP.

Hang timeout recovery, disconnect/reconnect, late cancellation, and HTTP
`after_response` session loss passed. The [earlier Java report](java-sdk-2.0.1.md)
contains the original malformed-response reproducer.

### Python: HTTP disconnect propagation

HTTP disconnect surfaced through the session context as a nested
`RemoteProtocolError('Server disconnected without sending a response.')`.
The harness accepted this as the disconnect signal; a fresh client completed `ping`
in all three repeats. Same-client recovery and error-free cleanup were not asserted.

## Manual verification

Start the published server:

```sh
npx -y mcp-failure-lab@0.12.0 serve
npx -y mcp-failure-lab@0.12.0 serve --transport http --host 127.0.0.1 --port 43123 --path /mcp
```

Run either command for the required transport. On a client that negotiated `2025-11-25`,
invoke `protocol_ping_liveness` with:

```json
{
  "pingAfterMs": 100,
  "livenessTimeoutMs": 1000,
  "completionDelayMs": 100,
  "closeOnFailure": false
}
```

Assert `protocolPing.outcome === "success"`, then invoke the `ping` tool on the same client.
For a confirmed `2026-07-28` connection, assert `unsupported`.
Check the negotiated version rather than the configured preference.

For malformed responses, use a fresh client per variant and record primary rejection and
follow-up recovery separately. For session loss, record activation, the next request,
session identifiers, reconnection, and cleanup separately.

## Scope exclusions

- `during_request` session loss, concurrent fault isolation, and soak testing.
- Failed-liveness HTTP closure.
- Legacy Go session-loss execution.
- Modern liveness for clients other than Go and C#.
- Controlled liveness rejection/timeout for clients other than TypeScript and Python.
- Authenticated external targets and `envFrom`; these belong to adapter verification.
- Validation of historical issue status or behavior in newer SDK versions.
