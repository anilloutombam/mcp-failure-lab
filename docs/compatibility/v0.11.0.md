or break the connection. C# cleanup took about 5.06 seconds in each run, matching its stdio
transport shutdown timeout; the other clients closed in under 11 ms.

TypeScript reported `fetch failed` for the interrupted activation request. Later use of that
session returned `Session not found`; the unrelated session and a new session both succeeded.

Python reported cancellation from the HTTP transport's task group. Calls on both client sessions
owned by the same surrounding task context then failed with `Connection closed` or the same
cancellation. Cleanup raised an `ExceptionGroup`, so reconnect was not attempted inside that
cancelled context. The TypeScript result and Failure Lab's integration tests distinguish this
client-context behavior from server-side session leakage.

## Interpretation

- All five clients ignored the late response as a result for the cancelled request and remained
  usable.
- `after_response` session loss was isolated to the selected session for both clients.
- TypeScript preserved an unrelated session during `during_request` loss and reconnected normally.
- Python's `during_request` loss cancelled the surrounding transport task context, affecting other
  sessions managed inside that context and its cleanup path.

## Scope

This is a focused check of the two v0.11.0 faults. `response_after_cancellation` was tested with all
five SDKs. `session_loss` was tested with the TypeScript and Python legacy HTTP clients; it is not
available over stdio or modern sessionless HTTP. Inspector, additional legacy HTTP SDK clients,
concurrency beyond two sessions, idle-session expiry, and soak behavior were not tested. The
earlier delay, timeout, malformed-response, duplicate-response, and disconnect results remain in
the [0.9.0](v0.9.0.md) and [0.10.0](v0.10.0.md) reports.
